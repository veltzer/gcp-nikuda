This is an analysis of the server and framework choices for nikuda on
Google App Engine, done in August 2026. The question was: is gunicorn the
fastest server? Is flask the fastest framework? The short answer is no and
no, and also that it does not matter for this app. The long answer follows.

Runtime version
===============
python314 is the newest runtime on App Engine standard (Preview November
2025, GA December 19 2025). We use it. When Google releases a newer
runtime, bumping the single line in app.yaml is all that is needed, after
checking the tests pass on that Python version locally.

Is gunicorn the fastest server?
===============================
No. Gunicorn with sync/gthread workers is middle-of-the-pack. Faster
servers exist:
	uWSGI (C)
	bjoern (C, WSGI)
	uvicorn (ASGI, uses uvloop)
	granian (Rust, serves both WSGI and ASGI)
In raw hello-world benchmarks granian or uvicorn can push several times
the requests-per-second of gunicorn with sync workers. App Engine standard
does not force gunicorn on us - the entrypoint just has to bind $PORT - so
something like 'granian --interface wsgi src.main:app' would deploy fine.

Is flask the fastest framework?
===============================
No. Among WSGI frameworks, falcon and bottle beat flask by roughly 2-3x on
routing/serialization overhead. Among ASGI (async) frameworks, starlette
and blacksheep beat it by more when the load is I/O-bound. FastAPI sits on
top of starlette and is a bit slower than bare starlette but still ahead
of flask. If "fastest possible Python" were the requirement, the 2026
answer is roughly granian or uvicorn serving starlette or falcon.

Why we keep flask + gunicorn anyway
===================================
Look at what the two endpoints actually do: a bisect over an in-memory
sorted list and a dict lookup - single-digit microseconds of work.
Per-request framework overhead for flask is a fraction of a millisecond;
the network round-trip to the user is tens of milliseconds. A rewrite to
an async stack would gain fractions of a millisecond per request, at the
cost of rewriting the app and the tests (webtest is WSGI-only, so the test
suite would have to move to httpx/ASGI testing too). Gunicorn with 2
gthread workers saturates an F1 instance's CPU long before the server
itself becomes the bottleneck. Flask + gunicorn is boring, first-class
supported by App Engine, and nowhere near our bottleneck.

What actually dominates latency on App Engine standard
======================================================
1. Cold starts. An F1 instance spinning up Python, importing flask and
	parsing all.json costs seconds. With max_instances: 2 and no
	min_instances we will hit them. If latency ever matters,
	min_instances: 1 (which costs money) buys far more than any
	framework swap.
2. Static file serving. Solved: the static_files handlers in app.yaml
	serve css/, images/, js/ and js_tp/ from Google's frontend without
	touching our instances.
3. Loading the dictionary. Solved: all.json is loaded once at module
	import, not on every request via before_request. That reload cost
	orders of magnitude more per request than any framework difference.

Configuration decisions that follow from this
=============================================
- entrypoint runs 'gunicorn -b :$PORT -w 2 --threads 4 src.main:app'.
	Google's guidance is to match workers to the instance class: 2
	workers for F1 (our implicit default). Threads make the workers
	gthread, which helps with concurrent I/O-bound requests.
- gunicorn must be listed in requirements.txt because the entrypoint
	names it explicitly (App Engine only provides it implicitly when no
	entrypoint is set). requirements.txt is generated by rsconstruct;
	the 'extra = ["gunicorn"]' setting in rsconstruct.local.toml adds it,
	and scanning only src/ keeps test-only imports (webtest) out of the
	deploy manifest.
- flask serves only the whitelisted asset directories over /static/
	(ASSET_DIRS in src/main.py, kept in sync with the app.yaml
	handlers), so src/main.py and src/data/ are not reachable over HTTP.
